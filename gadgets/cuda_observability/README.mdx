# cuda_observability

The `cuda_observability` gadget records factual CUDA Driver API returns and can
optionally derive bounded inference-activity timing candidates from launch and
copy patterns.

Raw `cuda_calls` output is unchanged when heuristics are enabled. By default,
every traced return is emitted. The explicit
`--emit-context-get-device=false` capacity-safe mode retains device caching and
complete aggregate statistics while intentionally omitting individual
`cuCtxGetDevice` records from raw output. The
`duration_raw` field is host API entry-to-return latency, not GPU execution
time. Candidate fields are not semantic TTFT, inter-token latency, token
counts, request IDs, or proof of GPU completion.

## Requirements

- Linux with eBPF privileges.
- An NVIDIA driver exposing the traced CUDA Driver API symbols.
- Host processes require `--host`; container workloads can be selected with
  the standard container filters.

The default mode emits factual CUDA calls:

```bash
$ sudo ig run ghcr.io/vfalico/cuda_observability:v0.1.0 \
    --host -o json
```

Enable inference candidates explicitly:

```bash
$ sudo ig run ghcr.io/vfalico/cuda_observability:v0.1.0 \
    --host -o json \
    --heuristics=true \
    --preset=generic-conservative-v1
```

The first heuristic record includes the effective preset, canonical
configuration, and its SHA-256 digest.

Request lifecycle correlation is a separate experimental, default-disabled
mode. It requires a version-1 marker library loaded into the same host process
that issues the CUDA calls:

```bash
$ sudo ig run ./cuda_observability.tar \
    --host -o json \
    --request-marker-library=/absolute/path/libig_gpu_request_marker.so
```

The marker protocol emits only a random process epoch and a domain-separated,
128-bit HMAC of the serving request ID. It never emits request text, tokens, or
the raw serving request ID. Validated lifecycle intervals are emitted only
after the bounded reorder watermark passes. Malformed, missing, duplicate,
overlapping, stale, or unknown markers emit bounded health diagnostics and
never manufacture request attribution. Raw CUDA records remain available.

Request-aware CUDA analysis is intentionally offline. While a valid request is
active, each factual CUDA return record carries hidden pseudonymous request
context and an exact-thread return sequence. Marker mutation during an in-flight
CUDA call invalidates the epoch. Each raw marker reports whether the kernel
accepted its state transition. Every accepted START resets the request-local
sequence, and an accepted END or ORPHAN carries the final successfully reserved
CUDA sequence. A pristine replay requires accepted READY, START, and END
transitions, stable zero loss generation, and exactly one event for every
sequence from 1 through that terminal value. It then replays the production
analyzer separately for each exact
`(host TGID, host TID, process epoch, request HMAC)` stream in return-sequence
order.
The gadget does not emit live request-attributed TTFT or cadence success
records, because independent datasource delivery cannot prove completeness.

The offline checker assumes an honest, exactly-once event collector. IG may
attach separate BPF map instances to multiple processes in one container; their
terminal map snapshots are summed with overflow checks and any observed failure
counter fails closed. Those snapshots are diagnostic rather than completeness
authority because map iteration can race still-active producers. Request-local
terminal sequence is the completeness authority. An omitted whole map instance
still cannot be discovered without an external attachment manifest.

## Raw telemetry

The gadget traces selected CUDA Driver API entry and return points, including:

- kernel and graph launches;
- host-to-device, device-to-host, and device-to-device copies;
- device-memory allocations and frees;
- stream, context, and event synchronization; and
- context device lookup.

Each `cuda_calls` record contains the return code, host-side duration, operation
metadata, and Inspektor Gadget process/container attribution. Bounded aggregate
rows report call, error, byte, duration, raw-emission, intentional-omission,
unmatched-return, map-update, and buffer-reservation counts by operation.

For high-rate serving workloads, opt into capacity-safe raw emission:

```bash
$ sudo ig run ghcr.io/vfalico/cuda_observability:v0.1.0 \
    --host -o json \
    --emit-context-get-device=false
```

This remains a CUDA-only gadget with no application hooks, but its per-call
`cuda_calls` stream is intentionally incomplete. `cuCtxGetDevice` probes still
update device attribution and aggregate calls, errors, and duration.
`intentionally_omitted` and `cuda_omitted` distinguish this configured omission
from `reserve_failures` and loss generation. Request-marker completeness replay
rejects filtered captures.

Raw CUDA calls can arrive in large bursts. Each attached eBPF instance therefore
uses a 128 MiB ring buffer for `cuda_calls`; the independent request-marker and
process-exit buffers remain smaller. Kernel memory scales with the number of
attached instances, so eight attachments reserve about 1 GiB for raw CUDA
events. Custom source builds may override the power-of-two
`CUDA_OBSERVABILITY_EVENT_RING_BYTES` compile definition, with a minimum of
1 MiB. A nonzero `reserve_failures` count means raw records were lost and any
request-aware completeness claim must fail closed.

## Heuristic candidates

Heuristics are disabled by default. When enabled, the Wasm analyzer groups
successful launch and bounded-copy observations into per-process activity
candidates. It emits:

- `inference_activity`: activity boundaries, first-decode candidates, and
  repeated-decode candidates;
- `inference_summary`: bounded activity summaries;
- `effective_config`: the exact configuration used for the run; and
- `analyzer_health`: capacity-eviction events.

State is bounded to 4096 active processes. The oldest state is evicted
deterministically when the bound is reached.

Use the generic preset unless a workload-specific preset exactly matches the
serving stack, model, GPU, and request shape it names. Process names never
select a preset automatically.

## OpenTelemetry

Datasource annotations expose bounded metrics and complete log records.
Important metric names include:

- `cuda.api.calls`;
- `cuda.api.duration`;
- `cuda.api.requested_bytes`;
- `cuda.inference.activity.events`;
- `cuda.inference.activities`;
- `cuda.inference.ttft_candidate`;
- `cuda.inference.decode_interval_candidate`;
- `cuda.inference.decode_candidate_count`; and
- `cuda.inference.activity_duration`.

Candidate metric names deliberately retain the `_candidate` suffix. They must
not be relabeled as serving-level TTFT or inter-token latency.

## Parameters

### `--heuristics`

Enable bounded inference-activity candidate analysis.

Default value: `"false"`

### `--preset`

Select an immutable analyzer preset. The generic preset is suitable for initial
observation; stack-specific presets are valid only for their named stack.

Default value: `"generic-conservative-v1"`

The experimental immutable preset
`vllm-0.10.2-qwen2.5-0.5b-a100-sequential-transition-v2` uses CUDA operation
transitions calibrated only for that exact sequential vLLM, model, and GPU
stack. The operation transition is the discriminator, so the legacy per-period
launch-count gate is disabled for this preset. Its repeated candidates estimate
content cadence; its first candidate remains a CUDA-derived heuristic and is
not a validated wire-level TTFT.

The newer immutable preset
`vllm-0.10.2-qwen2.5-0.5b-a100-sequential-transition-v3` adds directional
launch-to-D2H candidate coalescing before anchored deduplication. Its 3 ms
window is the whole-millisecond ceiling above the 2.277645 ms useful-pair tail
in the private calibration corpus. The first observed calibration cross-cycle
replacement was 31.968417 ms. These are descriptive observations, not general
runtime guarantees. The calibration corpus is not distributed in this source
repository, so these exact values are not independently reproducible here.

Private exact-stack validation passed 24 of 24 pristine sequential requests
with precision 0.9777, recall 0.9865, F1 0.9821, median absolute cadence error
1.274 ms, and p90 absolute error 1.626 ms against independent streamed-content
truth. The corpus is not distributed in this repository; the values are
disclosed as descriptive validation evidence rather than a reproducible public
benchmark. The preset remains experimental, default-disabled, and limited to
vLLM 0.10.2, Qwen2.5-0.5B-Instruct, an NVIDIA A100 80GB PCIe,
`max-num-seqs=1`, and one CUDA-emitting PID/TID. The validation does not cover
batching, concurrency, Ray, multiprocessing, other models, other GPUs, or
semantic token timestamps.

The experimental transition-v4 preset widens only the pair window to 6 ms. The
value is the whole-millisecond ceiling above the 5.037726 ms useful-pair tail
observed during residual analysis, while the first preserved cross-cycle pair
was 31.968417 ms. Private production-analyzer replay of the same 24-request
corpus removed all 10 false positives without changing any true positive or
false negative: precision 1.0, recall 0.9865, and F1 0.9932. Two batches were
held out from threshold selection and their candidate timestamps were
unchanged. The corpus is not included here, so these exact replay results are
not a public reproduction claim. The preset remains default-disabled and
requires fresh live validation before superseding transition-v3.

### `--request-gap`

Override the inactivity gap that closes an activity candidate as a Go duration.

### `--request-marker-library`

Enable experimental request lifecycle correlation by attaching
`ig_gpu_request_marker_v1` from the supplied absolute library path.

Default value: `""` (disabled)

This mode currently supports only a single CUDA-issuing vLLM EngineCore process
with sequential requests. The serving integration must use a random HMAC key of
at least 256 bits and must isolate every marker/logging failure from serving
behavior.

### `--request-marker-reorder-window`

Set the bounded boot-clock reorder window used before marker lifecycle records
become final.

Default value: `"50ms"`

### `--request-marker-state-timeout`

Set the maximum open marker lifecycle duration before fail-closed invalidation.

Default value: `"5m"`

### `--candidate-gap`

Override the quiet gap that qualifies a decode candidate as a Go duration.

### `--candidate-pair-window`

Enable experimental directional coalescing of an adjacent kernel-launch
candidate followed by a D2H-async candidate within this duration. The default
is disabled. This override requires the transition-v2/v3 operation masks and
`decode-min-launches=0`; select the named transition-v2 preset to enable it
manually, transition-v3 for the accepted 3 ms value, or transition-v4 for the
offline-reviewed 6 ms candidate.

An unresolved launch half is not emitted as a completed cadence candidate when
the activity closes. Instead, the gadget emits an `analyzer_health` record with
an `unresolved_launch_*` reason while preserving the underlying raw CUDA
telemetry.

### `--dedup-window`

Override the anchored candidate de-duplication window as a Go duration.

### `--prefill-min-launches`

Override the minimum observed prefill launches.

### `--prefill-min-copies`

Override the minimum observed prefill copies.

### `--decode-min-launches`

Override the minimum launches in a decode-candidate interval.

### `--candidate-max-copy-bytes`

Override the maximum device-to-host copy size eligible as candidate evidence.

### `--min-activity-offset`

Override the minimum time after activity onset before decode qualification.

### `--state-timeout`

Override the inactive-state timeout as a Go duration.

### `--max-activity-duration`

Override the maximum activity lifetime as a Go duration.

## Limitations

1. CUDA host calls are asynchronous with respect to GPU execution. This gadget
   does not measure kernel completion or GPU hardware occupancy.
2. Candidate boundaries are inferred from CUDA call timing and cannot identify
   semantic requests or tokens.
3. Concurrent requests in one process can overlap in the same process-scoped
   state. Use an independent request/wire timeline for semantic comparison.
4. Presets encode assumptions about a serving stack and workload. A preset may
   be inaccurate after changing model, batching, scheduler, GPU, or software
   version.
5. Missing uprobes, event-buffer pressure, or analyzer-capacity eviction can
   reduce observations. Check aggregate and analyzer-health records.
6. Decode-like CUDA cycles can precede the first streamed content. Operation-
   transition presets therefore do not make the first candidate an exact TTFT
   measurement.
7. A request `END` marker is scheduler lifecycle completion, not proof that all
   GPU work completed. Trailing CUDA activity must be measured separately.
8. Request correlation is invalid when request execution spans worker
   processes or when requests overlap in the CUDA-issuing process.
